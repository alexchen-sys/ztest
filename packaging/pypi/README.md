# PyPI packaging for ztest

Release wheels are built from **prebuilt static musl binaries** by
`scripts/build_wheels.py`. There is no `pyproject.toml` in the repository root on
purpose: ztest is a Zig program with a Python-compatible CLI, not a Python
package that happens to ship a binary. The only Python artifacts are the wheels
assembled here, and their metadata is generated by the builder so the wheel
layout, tags and hashes cannot drift away from what is actually shipped.

## Why a native wheel instead of a pure-Python shim

A `py3-none-any` wheel would have to ship Python code that compiles or downloads
the binary at install time — exactly the fragility ztest exists to remove. The
wheel therefore carries the executable itself:

```
ztest_runner/__init__.py                       # __version__, binary_path()
ztest_runner-0.5.1.data/scripts/ztest          # static musl binary, mode 0755
ztest_runner-0.5.1.dist-info/{METADATA,WHEEL,RECORD}
```

`pip` installs `.data/scripts/*` payloads into the environment's scripts
directory, so `pip install ztest_runner-*.whl` puts `ztest` in `<venv>/bin/ztest`
and `uvx --from ztest_runner-*.whl ztest` finds it in the ephemeral environment
without an entry-point shim. A `console_scripts` entry point was rejected
deliberately: it would pay a full Python interpreter start before `execve`,
which is the opposite of the ~1.2 ms supervisor start-up ztest sells.

## Platform tags

The binary is linked against musl and is fully static (`ldd` reports
"not a dynamic executable"), so it runs on glibc and musl distributions alike.
Each wheel therefore declares all three honest tags for its architecture, and
`pip` matches the most specific one available on the host:

| arch    | tags                                                                   |
| ------- | ---------------------------------------------------------------------- |
| x86_64  | manylinux_2_17_x86_64, manylinux2014_x86_64, musllinux_1_1_x86_64      |
| aarch64 | manylinux_2_17_aarch64, manylinux2014_aarch64, musllinux_1_1_aarch64   |

Resulting filenames:

```
ztest_runner-0.5.1-py3-none-manylinux_2_17_x86_64.manylinux2014_x86_64.musllinux_1_1_x86_64.whl
ztest_runner-0.5.1-py3-none-manylinux_2_17_aarch64.manylinux2014_aarch64.musllinux_1_1_aarch64.whl
```

`manylinux_2_17` is the floor rather than `manylinux1`: glibc never touches the
binary, so the tag only signals "any Linux that pip will install on". The static
payload makes `auditwheel`/`repair` unnecessary; do not run it, it would try to
bundle libraries that do not exist.

## Building

```sh
# dist/ must contain ztest-v0.5.1-linux-x86_64.tar.gz and ...-aarch64.tar.gz
python3 scripts/build_wheels.py --dist dist --verify
```

The builder:

1. reads the binary for each architecture out of the release tarball (or a bare
   `dist/ztest-<arch>` file for quick iteration). A bare `dist/ztest` is
   rejected: it carries no architecture. The payload's ELF header is validated
   before packaging — `EI_CLASS=2`, `EI_DATA=1` and `e_machine` (62 for
   `x86_64`, 183 for `aarch64`) must match the architecture being packaged, so
   a mislabelled tarball fails here rather than on a user's `aarch64` host.
2. writes deterministic zip entries (fixed 1980-01-01 timestamp, mode bits stored
   in the Unix external attributes, `create_system=3` so installers preserve the
   executable bit),
3. emits `RECORD` with url-safe base64 SHA-256 digests and appends/updates
   `dist/SHA256SUMS` without dropping entries it does not own,
4. with `--verify`, re-opens each wheel and re-checks every `RECORD` digest, the
   0755 payload mode, WHEEL-vs-filename tag equality, the absence of duplicate
   or mixed-architecture platform tags, and the payload's `e_machine` against
   the architecture the filename advertises. That last check is the only
   architecture gate an `aarch64` wheel can have on the `x86_64` CI runner,
   which cannot execute it.

METADATA declares `Requires-Python: >=3.11`, the same floor `README.md` states
for the runtime interpreter: the wheel installs a binary, but the worker
supervisor it spawns needs 3.11+, and a wheel that installs onto an interpreter
the shim cannot use would fail at first run instead of at install time.

## Verifying an installed wheel

`packaging/pypi/smoke_test.sh <wheel>` creates a throwaway venv, installs the
wheel, checks `ztest --version`, then runs a two-passing/one-failing suite and
asserts the exit code (exactly `1`) together with the reported counts
(`2 passed, 1 failed`), then repeats with a clean suite (`2 passed, 0 failed`,
exit `0`). CI runs the same script, so the manual and automated paths cannot
disagree.

## Publishing (manual, operator-gated)

```sh
python3 scripts/build_wheels.py --dist dist --verify
python3 -m twine check dist/*.whl
python3 -m twine upload --repository pypi dist/*.whl
```

Names `ztest-runner` (distribution) and `ztest-py` (reserved fallback) are the
intended public identities. Nothing in this repository uploads to PyPI
automatically: publication happens only on an explicit operator command, and the
GitHub release must exist first because `scripts/install.sh` resolves assets
from `releases/download/v<version>/`.

The CI `wheels` job writes the release payloads into `dist/` and uploads them as
one artifact: `ztest-v<version>-linux-{x86_64,aarch64}.tar.gz`, the two wheels,
`SHA256SUMS`, and `install.sh`. The installer is part of that set because
`scripts/install.sh` documents
`https://github.com/alexchen-sys/ztest/releases/latest/download/install.sh` as
its one-line entry point — publishing a release means attaching all of `dist/`,
not only the tarballs and wheels. `install.sh` is not listed in `SHA256SUMS`
(a bootstrap script cannot verify itself); the manifest covers the binaries.
